# 仕様（MVP・仮）

## 目的
AIニュースだけを、1枚ずつ縦スワイプで一目で読めるアプリ。情報源とツールを自分で選べる。「毎日開きたくなるか」を確かめる最小の形を作る。

## 仮定（決まっていないことはこれに従う）
- A1: ログインなし・外部DBなし。ユーザーの選択・保存・非表示（興味なし）はすべて端末内ストレージ（AsyncStorage）で管理し、外部サーバーに送信しない。
- A2: 表示・要約は **日本語＋英語**。収集時に日英ネイティブ要約を同時生成する。韓国語・スペイン語などは需要が出るまで作らない。端末側の機械翻訳は使わない。
- A3: 要約に使うモデルは `SUMMARY_MODEL`（環境変数）で切り替える。比較検証しやすいようモデル名は差し替え可能にする。
- A4: 最初のソースは `data/sources.seed.json` の公式ブログ系。RSSの有無は実装時に確認し、無いものは無効のままにする。
- A5: 見た目の確認用に、`data/seed_articles.json` から生成した `data/articles.json` のサンプル記事を使える。本番配信時も静的JSON（`EXPO_PUBLIC_FEED_URL`）を取得する形とする。
- A6: 下タブは「ホーム / 探索 / 保存済み / 設定」。探索はグリッド＋簡易キーワード絞り込み。
- A7: 自前スポンサード枠（AdMobなし）。`data/sponsored.json` の有効案件（同一広告主の複数文言パターン可）を、おすすめ／該当ツール・ソースのフィードにおおよそ4枚に1枚差し込む（先頭直後は出さない・初回は記事2件のあと）。カードは記事と同型で、必ず「広告」ラベルと公式／アフィリURLへのCTAを付ける。表示のON/OFFは不可（常時表示）。記事の `tool_tags`／`source_id` が案件と一致し、かつフィード内に該当広告カードがあるとき、右レールに製品アイコンを出しタップでその広告カードへスクロールする。個人データの外部送信・クリック計測SDKは使わない。
- A8: フィードの並びは **取り込み時刻（`created_at`）の新しい順**。公開日順だと新規取得した公式投稿が下に沈む。取り込みは `MAX_ARTICLE_AGE_DAYS`（既定7日）以内だけなので取得順でよい。カード上の日付表示は公開日のまま。

## 画面
1. **フィード（ホーム）**: 上部タブ「おすすめ / ソース別 / ツール別」。ソース別・ツール別は、チップ列と右端の「＋ 編集」（設定 > 情報源へ）。1枚ずつ縦スワイプ。並びは取り込み時刻の新しい順（A8）。おすすめ／探索は「ジャンル × ツール × 情報源」の掛け算（AND）で絞り込む。おすすめタブでは有効なスポンサードを稀に差し込む。
2. **カードの中身（上から）**: OGP画像 → 情報源の行（アイコン・ソース名・日付・ツール／ジャンル・件数）→ 見出し → 要約。右下に縦並びで、保存・共有・元記事・興味なし。画面長押しで元記事を開く。
3. **スポンサードカード**: 記事と同型。広告バッジ・広告主名・見出し・短文・CTA。興味なしボタンは出さない。保存は出さない。右下の空き枠に「他の広告」を置き、同じ製品の別スポンサードカードへジャンプする（フィード内に同じ製品の他カードが無いときは非表示）。
4. **設定 > 情報源**: ソースのオン・オフ、ジャンルとツールの選択。選択数を設定のトップに表示。表示言語は ja / en。スポンサー枠の表示切替は置かない。
5. **保存済み**: 保存した記事の一覧。
6. **探索**: 絞り込み後の記事をグリッド表示。簡易キーワード検索可（スポンサードは探索に出さない）。一覧の右側に縦スライドバーを置き、ドラッグで位置を動かせる（カード閲覧フィードには出さない）。

## 収集・要約
1. GitHub Actions の定期実行で、有効なソースのRSS等を取得する（Mac／端末に依存しない）。
2. URLとタイトルの類似で重複を除く。
3. 記事ページから og:image のURLを取得する（画像は保存しない）。
4. モデルに見出しと冒頭を渡し、JSONで返させる:
   - `title_ja`（おおよそ50〜70字、固有名詞と数字を入れる）
   - `summary_ja`（150〜200字前後、事実・仕組み・ビルダー向け結論）
   - `title_en`（14〜24語）
   - `summary_en`（95〜140語、日本語と同密度のネイティブ英語）
   - `tool_tags` / `genre_tags`
5. 要約は記事ごとに1回だけ作り、`data/articles.json`（`translations.ja` / `translations.en`）に保存して全ユーザーで共有する。品質ゲート（`npm run quality:check`）で英語の薄さを弾く。
6. 1日の件数（`MAX_ARTICLES_PER_DAY`、デフォルト **350**＝無料 Flash-Lite をやや攻めた目安、タイムゾーン既定 **America/Los_Angeles**＝Gemini RPD）と1時間の件数（`MAX_ARTICLES_PER_HOUR`、既定 **15**）と月の費用（`MAX_MONTHLY_COST_JPY`）に上限を設け、超えたら止める。さらにクォータ日内の経過時刻に比例したペース予算（`INGEST_PACE_SLACK` 既定 **6**）で均等配信し、先行しすぎによる空白を抑えつつ遅れ分を時間枠内で取り戻す。収集の**実行本体**は **GitHub Actions のみ**（Mac不要）。**主起動**は Cloudflare Workers Cron（`ops/ingest-wake-cf` → `repository_dispatch`、約15分。Vercel Hobby は日次制限のため主にしない。`docs/収集-外部cron手順.md`）。GitHub `schedule` は Sparse 保険（日2回。dispatch との二重消費を避ける）。無名 cron SaaS への PAT は使わない。1実行は `MAX_ARTICLES_PER_RUN`（既定 **4**）＋記事間隔 `INGEST_ARTICLE_DELAY_MS` で分割し、429は短く再試行したうえで連続したら実行を止める（空打ち防止）。
6b. **ソース偏りの抑制**: RSS と deferred（持ち越し）を1列にまとめ、優先度で並べて上から実行枠を埋める（レーン予約はしない）。優先順は (1) 直近 `SOURCE_SHARE_WINDOW`（既定 **100**）件の占有が `MAX_SOURCE_SHARE`（既定 **8%**）未満 (2) フィード累計件数の少ないソース (3) 公開日時が新しい (4) deferred は同条件ならわずかに先。1実行あたり同一ソースは原則 `MAX_ARTICLES_PER_SOURCE_PER_RUN`（既定 **1**）まで（候補が複数あっても今回は1件だけ載せ、残りは次回へ）。枠余り時はまず占有上限だけ外し、それでも余れば同一ソース上限を緩和して鮮度を確保。同件数グループ内のRSS順は実行スロットで回転。フィードの並びは取り込み時刻の新しい順のまま。
6c. **公開日ゲート**: 公開日（`pubDate`）が `MAX_ARTICLE_AGE_DAYS`（既定 **7**）より前の候補は、未登録でも取り込まない（古い公式投稿が枠を使うのを防ぐ）。日付が取れない候補はこのゲート対象外。
7. 品質失敗時の再試行は最大数回。レート制限（429）は指数バックオフで再試行する。
8. フィードは直近30日を目安に保持（期間切れは外してよい）。1ソース `maxArticlesPerSourceInFeed`（既定 **100**）と全体 `maxFeedArticles`（既定 **2000**）の超過は、**新規1件につき最大1件**だけ最古から押し出す（ソース上限オーバー優先、次に本数の多いソース。各ソース最低1・ツール最低保証あり）。一括で上限まで削らない。
9. アプリへの配信は `EXPO_PUBLIC_FEED_URL` 経由が本番想定（**GitHub raw 優先**。jsDelivr はキャッシュ遅れしやすいので主経路にしない）。開発中は未設定でも `public/articles.json` を都度取得。

ツール: `src/theme/tokens.ts` の `tools`（Claude, ChatGPT, Gemini, Cursor など）
ジャンル: `src/theme/tokens.ts` の `genres`（アップデート, 個人開発・収益化, マーケ・集客・ASO, SNS・ショート動画, 課金・ペイウォール, コスト・API料金, 開発, ビジネス, 画像生成, 動画, 音声, 研究, セキュリティ）

## 完了の条件
- 新しい記事が自動で取り込まれ、日英の見出しと要約が付く。
- 人が見て、事実の間違いが目立たない。
- スワイプで読め、保存・興味なし・元記事が動く。
- 情報源・ジャンル・ツールを選ぶと、おすすめ／探索の表示が変わる。
- 月の費用が上限を超えない。
